# 报告与机制解释

用于建立研究报告的论证主线、深化技术解释、编写作者学习材料，以及处理“看不懂”的反馈。写作和编辑统一采用 [writing-and-editing.md](writing-and-editing.md)，搜集资料、核对论断和处理来源冲突采用 [research-and-evidence.md](research-and-evidence.md)。市场趋势、技术细节与工作汇报先按 [task-narratives.md](task-narratives.md)选择论证任务，本文件再深化其中需要解释的关系与过程。

## 从已有材料和研究目标出发

先利用当前上下文确定要解释什么，已有信息足够时直接推进，不把下面的分流变成额外问卷。

- **有材料输入**：梳理文档、PPT、论文、笔记、数据和原图的结构，标记用户要求保留的内容、尚未解释的机制及会影响结论的缺口。保留来源顺序供反查；最终叙事可按目标读者重组。用户明确要求逐篇、逐章或忠实转述时遵守该要求。
- **从零开始**：先把题目拆成需要回答的研究问题，建立术语与第一批可靠来源，再确定章节和关键机制。根据证据改变提纲，不先写一套结论再寻找支持材料。
- **混合输入**：把用户材料与新检索材料接入同一证据记录，区分它们的来源、版本和状态。新旧材料口径不同，先解释变化再比较；不把重复转载算成独立验证。

文风参考只决定表达偏好，技术材料决定事实依据。用户指定的原文语气、引用、术语和领域格式应被保留；文档中缺失的细节不能由版式或写作模板补成事实。

## 分别确定读者、听众与作者基础

报告读者、汇报听众和讲述作者可能具有不同背景。记录他们已掌握的概念、需要形成的判断、应掌握的操作和主要阅读方式。负责人可能关心方案取舍，跨方向专家需要机制与接口，初学作者需要先看懂术语、步骤和原图；这些角色可以共享结论，但需要不同的铺垫。

下面的字段用于工作记录，不必以表单形式写进成品：

```text
成果/角色：报告读者 / 汇报听众 / 作者学习
已掌握：相关原理、术语、数学或系统经验
需补足：理解本次机制必需的知识
目标：形成什么判断；能解释或计算什么
阅读方式：摘要/正文/附录，页面/口述，基础单元/深入单元
```

知识层次依据材料与交流判断，不凭职位推定。尚未做过讲解或计算时，不把作者状态记录为“已掌握”。

## 从问题与依赖建立结构

先确定研究要解决的趋势判断、路线比较、能力解释或具体决策，再选择系统主线。技术报告可沿工作负载、关键机制、实现资源、运行方式、效果与演进展开；器件、协议、软件、产业、政策或实验研究应按自身关系组织，不硬补不存在的系统层次。

不同任务需要解释的中间环节不同：市场趋势要说明变化的证据、驱动及情景条件；技术细节要说明原理怎样落实为实现和系统效果；工作汇报要说明结果相对目标的偏差、原因与措施。按本次判断选择解释深度，市场和工作汇报无需先完成一套芯片或软件机制教程；其中某个技术约束决定结论时，再展开必要机制。

章节之间交代实际依赖。例如，前一章解释了候选如何生成，下一章再说明各位置如何选择；前一章得到局部结果，下一章解释归并；前一章配置了资源，下一章讨论运行时状态如何维护。时间线适合说明版本和条件的变化，但技术演进还需解释旧约束、新条件及当前取舍之间的关系。

区分通用原理、对象的具体实现和对先进性的判断。先交代通用方法，再说明当前对象改变了哪些表示、操作、接口或资源安排，最后在共同条件下讨论收益与代价。组合成熟技术也可以解决重要问题；是否领先、创新或不可替代，需要各自的比较依据。

多个来源可形成综合判断，但应把推导写出来。某一组件的局部改善怎样传递到系统，是需要解释的关系：减少了哪部分工作，哪些步骤仍然存在，资源是否共享，瓶颈是否转移。不要从一个局部指标直接跳到整套系统或产业结论。

## 同一套研究内容如何进入四类成果

研究记录、机制说明和数据应保持同一事实基础，四类成果按用途组织内容，不做逐段机械缩写。

- **报告**保留判断所依赖的证据、机制、条件与比较。正文深入影响结论的部分，基础定义、完整参数或长推导可以进入附录。摘要和综合结论应在机制正文完成后重写。
- **PPT**按页面的解释任务选择图表和文字。高密度页中的细节应有层级、阅读顺序和共同主题；复杂架构可以分视角讲解，同时保留全图供定位。页内可用完整判断、短段落或分类项目符号，保留使图表和比较成立的条件与解释。标题可概括内容、提出问题或陈述有依据的观点，并接上全场主线。
- **汇报稿**默认形成可照读的文本，沿最终页面的读序完成定位、跟踪、比较、解释和转场。每页可以有不同节奏，不必反复复述相同背景。指图文字须与最终图面一致；备注同步与时长规则分别见 [briefing-and-teaching.md](briefing-and-teaching.md)和 [presentation-pacing.md](presentation-pacing.md)。
- **作者技术解析**形成连续学习材料，从必要基础走到实际操作、算例、跨层机制和系统效果。另留 PPT 页码、图号与解释单元之间的反查关系，避免把详解写成互不相连的逐页注释。

同一论断在不同成果中可以压缩，但对象、单位、证据性质和成立条件必须一致。压缩后若听众无法理解图中关键关系，应增加解释位置或关联页，而不是用抽象形容词占位。

## 纯报告的完成路径

只请求报告时，沿“研究问题与证据 → 章节论证 → 正文及图表 → 摘要与结论 → 最终文件检查 → 写回项目状态”完成本轮。PPT、页面计划、备注和演讲时间均不适用，不为通过检查而创建空文件。Word、PDF或Markdown按实际请求交付，不自动增加其他格式。

成稿后对照问题覆盖，确认各项回答有章节落点，关键事实和图表有就近引用，引用能回到实际读过的来源位置。未解问题保留其对判断的具体影响。摘要与建议由已完成论证形成，不在压缩时扩大确定程度或增加新证据主张。

正文定稿不等于转换成品已完成。以本次采用的文稿为基线，对照最终文件中的章节、关键限定、表格行列、公式、图注和参考文献；目录、交叉引用与显示编号在最终排版后更新。按[质量与版本](quality-and-versioning.md)检查实际格式，再更新成果清单、检查回执与恢复入口。后续内容修改使受影响的摘要、图表、引用和检查重新待核。

## 解释深度与机制工作卡

以下深度用于定位解释缺环，按受众与领域选择，不要求每段都写满四层。

1. **概念**：它处理什么输入、产生什么输出、位于系统哪里、回应什么需求。
2. **机制**：一次操作怎样经过各步骤，中间结果和状态如何变化，设计为什么有效。
3. **实现**：上述动作由哪些算法、数据结构、电路、资源或接口执行，怎样对应到原图。
4. **系统**：上下游、配置、负载与运行条件如何共同影响质量、时间、资源和取舍。

关键机制宜达到与核心判断相称的解释深度。专家报告的重要实现差异通常需要实现层和系统层；背景页可以只到概念层。公开材料只支持到某一层时，在相关位置说明依据范围，随后解释已知部分；不以重复免责声明代替讲解，也不补造不可见的内部实现。

在工作记录中保留机制卡，再组织成自然段落、图注或讲解；卡片字段不要原样堆满正文。

```text
机制与主张：名称、要解释的判断、目标深度
系统位置：输入 → 操作 → 输出；执行者与相关状态
动机：具体重复工作、瓶颈、约束或需求
关键改变：原做法与当前表示、操作、资源安排的差异
执行过程：步骤、存取、选择、控制、中间结果及状态变化
局部影响：减少、增加或保留的工作与资源
系统传递：上下游依赖、共享资源、关键路径及适用条件
依据与映射：来源位置、原图标号、算例步骤、待补环节
```

## 前置知识放在首次需要的位置

为复杂机制建立最短知识链：必须先理解什么，在哪里首次解释，它帮助读懂哪一步或哪张图。只补读者缺少的环节，不在每章重复基础定义。概念相互依赖时，先用最小模型定义对象，再逐步加入真实条件。

例如理解读缓存，先明确源数据、键、缓存副本、有效期和更新事件，再说明命中、过期与校验。理解一个协议栈，先明确传递的数据单位、端点与各层职责，再讲封装、传输和接收端处理；层名本身不能说明数据经历了什么。

首次使用公式前定义符号、维度、索引起点、单位和必要假设。英文缩写按受众需要展开；能用既有术语准确表达时，不另造中文标签。可增加能暴露理解缺口的问题及答案位置，但不要强制每个术语配一道题。

## 跨层机制要接上接口与状态

软件、算法、硬件与运行环境之间的交界常是理解断点。关键接口需接好两端：谁生产、谁消费，传递的对象及表示是什么，何时产生和何时可用，谁负责转换、存储及维护状态。区分初始化或配置时固定的内容与每次执行中变化的内容。

例如软件提交的可能是地址、描述符或编码，硬件根据它进行存取、选择或计算；从“提交任务”继续往下解释时，应指出实际提供了什么，以及何种事件表示任务完成。同步调用、异步入队、传输完成与计算完成可能是不同事件，必须按具体实现区分。

跨层推导同时跟踪控制和数据。图上的一条连线可能表示数据传输、控制依赖、物理连接或逻辑关联；不能只凭箭头推断协议、缓存、带宽或并行执行。公开资料未提供的接口细节保留为待补环节，不用常见实现填空。

讨论系统收益时，说明局部操作与总体时间的关系。串行步骤、可重叠步骤、共享带宽和等待条件需要分别处理；沿关键路径或相关资源推导。只知道计算次数减少，尚不足以得到端到端时延比例；可以明确指出还需测量或计算的环节，并继续解释现有结论。

## 图表讲解：先读对，再用于论证

选图后先看完整原页、图注和邻近说明，确认图描述的对象、版本、场景与证据性质。示意图、架构图、测量曲线和规划路线图支持的判断不同。专业原图的标签、图例、坐标、单位、面板关系和关键细节需要保留；裁剪与翻译不能改变它所支持的结论。

按图的任务选择读法，必要时完成以下动作，而不是给所有图套同一段讲稿：

- **定位对象**：图处于系统哪个尺度，展示逻辑结构、物理部件、运行过程还是测量结果。
- **解释编码**：颜色、线型、箭头、框、符号、坐标轴和单位分别代表什么；未定义的颜色不自行赋予含义。
- **跟踪一个实例**：沿一个输入、数据块、请求或样本走过相关标签与路径，并与正文步骤、算例中的对象一一对应。
- **完成必要比较**：说明比较的是哪个条件、组别、阶段或方案，差异出现在哪里，哪些口径必须一致。
- **回到当前判断**：指出图中哪一部分支持哪项结论，以及结论的必要条件。图片只展示结构时，不能据此宣布实测性能提升。

复杂图可以先给完整视图定位，再放大关键区域；保留原图标号与局部的关系。原图中的文字即使不能直接提取，也要通过视觉阅读确认，不能靠猜测或相似图补齐。看不清或对应不上时，换更清晰来源、扩大局部或如实记录缺口。

图注与口述分工：图注让离开讲解的读者也能识别对象、条件与来源；口述带听众沿图完成一次阅读。不要用“图很直观”“充分展示优势”代替具体标签与技术关系。

## 完成一次操作，并贯穿系统

选择足够小、同时保留关键关系的例子。先写明这是来源中的真实案例、依据原式复算，还是教学假设。说明输入与初始状态，逐步得到中间结果、状态变化和输出；随后把例中的对象映射到真实模块、图号和标号。教学值不能混入产品规格或测量结论。

数学例子要能复算，电路例子要跟踪访问、控制、信号与输出，软件例子要说明输入契约、数据结构、调用和状态变化。只在学习所需的粒度展开，不用与判断无关的实现细节增加篇幅。

改变一个有意义的条件，再沿同一过程推演影响。例如改变输入、共享方式、并发、数据规模、批量或失效策略；保持其他假设清楚，避免同时改变多个变量后把结果归因于其中一个。

长篇系统报告宜选择主算例贯穿关键层次。局部例子用于解释困难机制，随后接回同一输入到输出的过程。内部可记录步骤、输入表示、执行者、动作、中间结果、输出及来源，防止各章悄悄更换单位、索引、数值或假设。

### 教学主算例：有效期怎样同时影响后端访问与新鲜度

假设只考虑顺序读请求，键 K 的缓存起初为空，有效期 60 秒；命中且未过期时直接返回缓存值，缺失或过期时读取后端并重新计时。为简化过程，忽略读写耗时；后端在第 40 秒由 V1 更新为 V2，更新不会主动通知缓存。条目在到期时刻及之后视为过期。

- 第 0 秒：读取后端 V1，缓存条目写为 `(K, V1, 到期时刻60)`，返回 V1。
- 第 20 秒：当前时间小于 60，返回缓存 V1，不读取后端。
- 第 50 秒：条目仍有效，返回 V1；它与后端此时的 V2 不同。
- 第 70 秒：旧条目已过期，读取 V2，更新到期时刻为 130，返回 V2。

结果为 V1、V1、V1、V2，对应两次后端读取。与每次均访问后端的教学对照流程相比，后端读取从四次减少到两次；第 50 秒的响应仍是旧值。这两个现象都由有效期内复用缓存值产生，因此选择有效期时需要同时考虑后端访问负载与允许的旧值持续时间。例子没有测量请求时延，不从访问次数推出时延改善比例。

这个例子可贯穿键生成、请求路由、条目表示、时钟判定、后端访问、状态更新与响应输出。若把有效期改为 30 秒，可沿同样的四个时刻重新计算，再比较访问次数和返回值。真实系统还有并发、失效通知、淘汰或一致性协议时，分别加入并说明它改变了哪一步，不把本模型推广为全部缓存行为。

## 区分逻辑表达与物理实现

先解释哪个位置、该位置表达什么，再解释这种关系如何实现。地址、存储索引、被引用数值、当前运算结果和物理单元可能是不同对象，应分别定位。按类别排列的示意图不等于实际物理布局，图中靠近也不自动证明两部件直接相连。

例如图的一侧列出候选类别，另一侧按参数位置引用候选：前者按类别组织，后者按使用位置组织。可以选一行读出，再换输入重算，说明哪些关系保持、哪些值变化。具体选取顺序来自原图；不能为方便讲述调整连接后继续声称是原实现。

同一功能可能由固定连接、可编程选择、存储编码或其他结构完成。具体资料支持哪种实现，就沿那种实现说明信号经过哪里、数据从哪里读取、选择和计算发生在哪里。借用通用模型解释时标出模型与对象的对应及差异。

## 数字、量级与技术比较

重要数字可以配一个与当前任务有关的尺度参照，例如将容量换算成可存储记录数，或用数据量与带宽估计理想发送时间。先定义单位和假设，记录计算方法；参照只帮助建立量级直觉，不冒充实际测量。

技术比较至少检查影响结论的口径：bit/Byte、十进制/二进制容量、单向/双向、每端口/每芯片/每系统、峰值/持续值、算力精度及稀疏条件、请求批量、质量要求、平均值/分位数、已发布/规划。按当前对象选择相关项，不为每段附上全部检查表。

测量、推算、作者解释和厂商主张分别标明。资料可以支持一个局部关系，而不足以支持全面排名；此时按维度给出比较与待补证据，继续说明已有机制。表格中的空缺也应保持其真实状态，不用类比值填齐。

## 作者声音与学习节奏

以承担解释责任的作者语气写作，使用平实的领域中文。写清材料展示了什么、本次进行了什么计算、哪些是推导；第一人称活动必须有实际记录。不要因为希望“像研究者”而虚构实测、部署经验或访谈。

讲解先给当前需要的对象，再完成一轮操作，随后增加条件。复杂判断可以分段推导，重要结果可以用短句突出；篇幅服从理解负担，不强制每节同样长度。精简时保留前置知识、接口、中间结果和原图映射，去掉重复评价、预告和没有作用的总结。

初学者需要类比时，说明类比对象与真实对象的对应，用它帮助推导一个结果，再回到机制。类比若引入错误关系，改用小算例；无需每个术语都配比喻。公式、专业名词和图中细节可以保留，只要解释其作用和使用位置。

## 长篇详解与掌握检查

作者技术解析应能顺着知识路径连续阅读：先补足必要基础，再进入表示与操作、特色机制、跨层运行和系统效果。具体顺序随研究对象调整。PPT 页码映射作为反查索引，正文合并重复基础，章节自然承接已得到的结果。

按实际发生的讲解或计算记录状态；未检查则写“待检查”，不要声称作者已经掌握。可用以下能力选择代表性的自检任务：

- 用自己的话说明对象、动机和输入输出。
- 独立复算关键步骤、中间结果及单位。
- 沿原图的真实标签和路径解释一次操作，并映射到算例。
- 改变输入、规模、策略或状态，解释影响如何传递到结果和系统取舍。

需要学习材料时可提供有答案的检查题，题目针对实际难点，例如某个标签表示什么、一个数如何算得、某个状态何时更新。它们属于内容设计；未经实际执行，不把它们写成已完成的验证。

收到“看不懂”时，先定位断点：缺前置概念、主语不明、接口未接上、图文不对应、中间步骤省略，或单位与假设未定义。再决定补定义、重排、换图、放大局部或增加算例，不仅把原句换成更口语的同义表达。

机制正文完成后，回看研究问题，重写摘要和路线判断，并检查报告、PPT、讲稿与技术解析使用的术语、数字、条件及图号是否一致。解释深度和篇幅围绕研究目的分配，不靠统一章节模板凑齐形式。
